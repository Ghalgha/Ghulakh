# Многопоточный TURN datapath

## Цель

Один логический VPN-туннель должен использовать несколько независимых TURN allocations через VK Calls. Ограничение пропускной способности отдельного relay-потока нельзя обходить созданием дополнительных потоков ОС поверх одной allocation: для масштабирования нужны независимые allocations, каждая со своим UDP socket, TURN allocation, permission, ChannelBind и защищённой сессией.

Многопоточность является обязательной частью целевой архитектуры. Количество путей не фиксируется по числу потоков CPU и не выводится из числа групп в сторонних реализациях.

## Термины

- **Tunnel group** — одна логическая VPN-сессия устройства с одним виртуальным IPv4, одним Android TUN и несколькими transport paths.
- **Transport path** — независимая VK Calls TURN allocation, UDP socket, peer permission, channel binding, Noise handshake, directional AEAD keys и собственные очереди.
- **Worker** — ограниченный набор задач обработки одного path. Число async tasks не тождественно числу OS threads; Tokio runtime управляет исполнением задач на пуле потоков.
- **Flow** — IP-поток, определяемый адресами, протоколом и портами (для фрагментированных IPv4-пакетов — с учётом IPv4 identification).

## Создание tunnel group

1. Android генерирует случайный 128-битный идентификатор tunnel group на время жизни VPN-сессии.
2. Для каждого path клиент создаёт отдельный защищённый UDP socket и отдельную TURN allocation.
3. Внутри третьего зашифрованного сообщения Noise передаются tunnel credential, group ID, path ID и запрошенное число paths. Метаданные не передаются открытым текстом.
4. Сервер проверяет credential, ограничивает допустимое число paths, резервирует один виртуальный IPv4 для group ID и возвращает его в зашифрованном ServerAck.
5. Все paths одной группы получают один виртуальный IPv4 и MTU, но независимые session IDs и ключи.
6. Повторный path ID в той же группе отклоняется. Несовпадающие path count/параметры группы отклоняются. Группа освобождает адрес только после удаления последнего path.

Group ID — идентификатор экземпляра туннеля, а не учётные данные и не секрет. Он принимается только внутри успешно аутентифицированного Noise handshake. Разные установки приложения не должны объединяться только из-за совпадения пользовательского tunnel credential.

## Распределение uplink

- Android TUN читается одним владельцем; пакеты поступают в ограниченную очередь диспетчера.
- Диспетчер выбирает один здоровый path на пакет с учётом доступности, очереди и наблюдаемой перегрузки.
- Потоки распределяются между paths; нельзя использовать простой round-robin по каждому пакету без механизма восстановления порядка.
- Для возможности отправлять пакеты одного IP flow по разным paths каждый пакет получает монотонный group sequence внутри защищённого payload. Sequence общий для группы, а не для отдельной allocation.
- Сервер проверяет AEAD и session/path identity, затем передаёт кадры в ограниченный reorder buffer группы. Буфер выдаёт пакеты TUN по group sequence; пропуск не блокирует трафик бесконечно — действует ограниченный gap timeout и лимит памяти.
- Повтор sequence, слишком старые кадры и выход за окно отклоняются. Повторная передача на уровне TURN не подменяет семантику UDP; восстановление потерянного IP-пакета остаётся задачей транспортов верхнего уровня.

## Распределение downlink

- Сервер читает TUN одним владельцем и определяет tunnel group по destination IPv4.
- Диспетчер выбирает здоровый path группы, добавляет общий downlink group sequence и шифрует пакет ключами выбранного path.
- Клиент проверяет path/session AEAD, затем использует отдельный bounded reorder buffer группы перед записью в Android TUN.
- При отказе path новые пакеты перенаправляются через оставшиеся paths. Активные allocations не считаются доступными, пока не завершены TURN setup и Noise authentication.

## Параллелизм и владение ресурсами

- Каждый path имеет собственного socket actor: один reader и сериализованный writer на его UDP socket. Сокет нельзя читать параллельно из нескольких независимых задач.
- Paths независимы друг от друга; один медленный relay не должен блокировать очереди остальных.
- TUN reader/writer остаются единственными владельцами Android TUN I/O. Между TUN и paths используются bounded queues и явные счётчики drops/backpressure.
- Для запуска paths используется ограниченный concurrency gate и pacing, чтобы не создавать burst запросов к VK Calls.
- Потоки ОС, число Tokio worker threads и число TURN paths — три разных настройки. Сначала фиксируется безопасная архитектура, затем значения подбираются измерениями.
- Потеря одного path деградирует группу, а не завершает VPN, пока остаётся хотя бы один аутентифицированный path. Потеря всех paths переводит tunnel group в recovery.

## Политика распределения

Начальная реализация должна обеспечивать:
- минимум два независимых paths в активной многопоточной конфигурации;
- верхний предел числа paths, заданный конфигурацией сервера и клиента;
- flow-aware weighted deficit scheduling, чтобы не перегружать один path;
- приоритет коротких управляющих/ACK-пакетов без бесконтрольного обхода очередей;
- bounded flow table с TTL и безопасным поведением при переполнении;
- отдельные метрики для каждого path: bytes, packets, queue depth, queue drops, send errors, RTT/progress gaps, authenticated receive rate.

Никакие численные значения пропускной способности VK TURN не считаются гарантированными без измерений. Нельзя жёстко задавать вес path по предполагаемой скорости. Контроллер должен опираться на измеряемую доставку и перегрузку.

## Этапы реализации

1. Добавить защищённый формат client session context: group ID, path ID, requested path count.
2. На сервере реализовать lease виртуального IPv4 и регистрацию нескольких session IDs в одной tunnel group.
3. На клиенте реализовать TurnPath и TurnPathGroup, поднимающие независимые protected UDP sockets и TURN allocations.
4. Реализовать общий group sequence и bounded reorder buffer в обоих направлениях.
5. Реализовать диспетчер path selection и деградацию/восстановление отдельных paths.
6. Добавить mock end-to-end тесты для двух и более paths: распределение пакетов, порядок, потери, duplicate/replay, path failure, восстановление, queue saturation и cleanup последнего path.
7. Только после успешной программной вертикали провести физические Android/VPS испытания и измерить масштабирование.

## Поздние функции

После успешного завершения основного проекта:
- **Профили энергопотребления:** экономичный, сбалансированный и производительный режимы. Они должны управлять числом активных TURN paths, concurrency, batching, keepalive cadence и worker scheduling. Профили не должны отключать обязательную защиту или нарушать восстановление.
- **Тест скорости:** измеряет upload/download, latency, jitter, loss, число активных paths и вклад каждого path. Тест должен отличать суммарную скорость нескольких потоков от скорости одного потока и не выдавать синтетические результаты за реальную производительность.
- Настройки профилей и тест скорости добавляются только после подтверждения устойчивости многопутевого туннеля.

## Ограничения и риски

- VK Calls может ограничивать число одновременных allocations, частоту запросов или суммарную пропускную способность. Это пока не подтверждено физическими испытаниями.
- Несколько TURN allocations увеличивают расход памяти, сокетов, keepalive-трафика и CPU.
- Глобальный reorder buffer добавляет задержку и head-of-line blocking при потере одного кадра; размер окна и gap timeout должны быть ограничены и измерены.
- Если сервер или клиент перезапускается, старые group IDs и paths не восстанавливаются как действительные сессии; выполняется новая аутентификация.
- До тестов нельзя обещать линейный рост скорости от числа paths.
