# Архитектура

## Цель

Система состоит из Android-клиента, сервера и общего протокольного слоя. Управляющие сообщения и пользовательские данные логически разделены.

## Компоненты

### Android

- Kotlin UI и управление состоянием.
- Android `VpnService` для создания локального TUN-интерфейса.
- Kotlin JNI facade для общего Rust transport core; сетевые вызовы выполняются вне UI-потока.
- Конфигурационный профиль хранит credential и DER trust anchor в AES-GCM-шифротексте, ключ — в Android Keystore.
- UI умеет импортировать X.509 trust anchor и проверять соединение; создание VPN-туннеля ещё не подключено.
- Изолированный транспортный адаптер.
- Секреты должны храниться в Android Keystore; JNI не должен логировать credentials. Фактическая интеграция Keystore ещё не завершена.

### Сервер

- Rust async runtime.
- TLS-защищённый управляющий канал.
- Реестр устройств и отзыв индивидуальных учётных данных.
- Ограничения размеров, частоты запросов и числа сессий.
- TUN и маршрутизация пользовательских пакетов — отдельный этап; до его завершения сервер не заявляется как полноценный туннель.

### Протокольный слой

- Версионированные сообщения.
- Ограниченные длины и строгая валидация.
- Неизвестные обязательные поля и версии отклоняются.
- Идемпотентность и защита от повторного воспроизведения задаются для каждого типа сообщения.

## Транспорт

Первичная реализация использует QUIC поверх TLS 1.3. Криптографический handshake делегируется проверенной реализации QUIC/TLS. Не вводить собственный handshake поверх TLS без отдельного анализа и спецификации.

Для пользовательских данных выбран QUIC DATAGRAM. Общий протокольный crate уже содержит ограниченный бинарный framing v1 для IPv4/IPv6 и проверяет длины IP-заголовков. Перед отправкой клиент обязан учитывать фактический `max_datagram_size` QUIC-соединения. Серверный цикл уже одновременно обслуживает управляющие потоки и принимает датаграммы, проверяя аутентификацию и framing. При включённом серверном TUN валидные IPv4-пакеты проходят source-IP проверку, egress ACL и ограниченную очередь; обратные пакеты направляются по назначенному адресу клиента. TUN выключен по умолчанию, IP forwarding и NAT настраиваются администратором отдельно. Надёжный управляющий поток остаётся отдельным.

## Модель расширения

Транспорт реализуется за интерфейсом, который отделяет:
- установление аутентифицированной сессии;
- отправку/приём датаграмм;
- жизненный цикл соединения;
- диагностику и метрики.

Новый транспорт не должен менять модель идентичности, формат конфигурации или бизнес-логику Android-клиента.
