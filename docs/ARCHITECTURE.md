# Архитектура

## Цель

Система состоит из Android-клиента, сервера и общего протокольного слоя. Управляющие сообщения и пользовательские данные логически разделены.

## Компоненты

### Android

- Kotlin UI и управление состоянием.
- Android `VpnService` для создания локального TUN-интерфейса.
- Kotlin JNI facade для общего Rust transport core; сетевые вызовы выполняются вне UI-потока.
- Конфигурационный профиль хранит credential и DER trust anchor в AES-GCM-шифротексте, ключ — в Android Keystore.
- UI умеет импортировать X.509 trust anchor и проверять QUIC-соединение.
- JNI facade предоставляет назначенный IPv4, признак готовности серверного TUN, отправку и приём IP-пакетов.
- VpnService создаёт локальный TUN после успешной аутентификации и двух серверных флагов готовности (TUN и административное подтверждение forwarding), устанавливает full-tunnel IPv4/IPv6 маршруты и соединяет потоки чтения/записи с JNI.
- QUIC UDP-сокет защищается методом `VpnService.protect` до установки маршрутов.
- Секреты не передаются в логи и хранятся в Android Keystore. Автоматическое восстановление соединения после смены сети ещё не реализовано.

### Сервер

- Rust async runtime.
- TLS-защищённый управляющий канал.
- Реестр устройств и отзыв индивидуальных учётных данных.
- Ограничения размеров, тайм-ауты, лимиты числа соединений и потоков.
- Опциональный IPv4 TUN с адресным пулом на сессию, ограниченной очередью, source-IP validation и обратной маршрутизацией по адресу назначения.
- IP forwarding/NAT/firewall не меняются автоматически; IPv6 forwarding отключён.

### Протокольный слой

- Версионированные сообщения.
- Ограниченные длины и строгая валидация.
- Неизвестные типы сообщений и версии отклоняются.
- Для команд с побочными эффектами отдельно задаются идемпотентность и защита от повторного выполнения; транспортная replay protection сама по себе не заменяет прикладные проверки.

## Транспорт

Первичная реализация использует QUIC поверх TLS 1.3. Криптографический handshake делегируется проверенной реализации QUIC/TLS. Не вводить собственный handshake поверх TLS без отдельного анализа и спецификации.

Для пользовательских данных выбран QUIC DATAGRAM. Общий протокольный crate уже содержит ограниченный бинарный framing v1 для IPv4/IPv6 и проверяет длины IP-заголовков. Перед отправкой клиент обязан учитывать фактический `max_datagram_size` QUIC-соединения. Серверный цикл одновременно обслуживает управляющие потоки и принимает датаграммы, проверяя аутентификацию, framing, назначенный source IP и egress ACL. При включённом серверном TUN валидные IPv4-пакеты проходят source-IP проверку, egress ACL и ограниченную очередь; обратные пакеты направляются по назначенному адресу клиента. TUN выключен по умолчанию, IP forwarding и NAT настраиваются администратором отдельно. Надёжный управляющий поток остаётся отдельным.

## Модель расширения

Транспорт реализуется за интерфейсом, который отделяет:
- установление аутентифицированной сессии;
- отправку/приём датаграмм;
- жизненный цикл соединения;
- диагностику и метрики.

Новый транспорт не должен менять модель идентичности, формат конфигурации или бизнес-логику Android-клиента.
